# 图片获取与预取修复结果

本次实施诊断报告建议的第1、2项。没有加入城市轮换、每日挑战、提示、个人纪录或排行榜。

## 已修改的行为

### API和图片准备

- HTTP请求成功但JSON中包含API错误时，显式抛出带错误代码的异常，不再保存为六小时空图片池。
- 城市查询先获取原文件资料，过滤MIME、尺寸和质量，并做图片家族去重；不为TIFF等不支持的文件请求缩略图。
- 选中合格文件后，单独请求它的缩略图和署名资料，一次准备并缓存。单个文件失败会隔离五分钟，并尝试同城其他文件，不丢弃整座城市。
- 同一城市的资料缓存构建串行合并，避免多个玩家同时重复构建。
- 已有有效图片池刷新失败时，保留旧数据，最多在规定的24小时有效保留期内使用；城市刷新失败短暂退避，真实空池只缓存五分钟。
- 遇到HTTP429或503时尊重Retry-After；JSON限流或maxlag错误也有短暂退避，不在前台不断重试。

### 预取和近期历史

- 已完成预取先检查最新图片、城市历史。与历史冲突的结果会被丢弃，包括仅为页面预加载而读取结果的情况。
- 没有可用预取时先选择已准备好、符合排除历史的动态图片，不联网；没有这种图片才等待最多0.3秒，最后才使用固定本地题。
- 未完成任务保留，之后读取时再次检查历史；已完成但冲突的任务可以被新的预取任务替换。
- 图片排除历史扩大到100题，城市历史保持20题，均跨局保存。避免快速读取已见缓存图片形成短周期循环。
- 固定图片和动态图片使用相同源文件身份。旧版本local标识自动转换，保留已有得分和进度。

## 实际联网验证

通过修复后的 `_fetch_photos` 和 `_add_credit` 路径低频请求，每城取资料一次、抽查文件一次。

| 城市 | 图片家族去重后的候选数 | 单个文件缩略图和署名 |
|---|---:|---|
| 开罗 | 33 | 成功 |
| 都柏林 | 38 | 成功 |

候选数与此前54、39个质量筛选通过文件的口径不同：本表已经执行图片家族去重。并非全部候选都已准备缩略图或经人工视觉审核；没有假称浏览器加载已验证。

证据：`after-network/summary.json`、`after-network/trace.json`。

## 回放验证

以下均为原有Flask路由的受控回放，固定准备耗时0.6秒，合成图片池100城每城20张，无网络。每个场景只比较各一次100题回放，存在随机及线程调度波动，不是日常玩家发生率。

| 场景 | 实施前 | 最终版本 |
|---|---|---|
| 极速冷启动无尽模式 备用题占比 | 50% | 50% |
| 极速冷启动 图片唯一率 U_I(100) | 70% | 70% |
| 极速冷启动 图片重复率 R_I(50) | 42% | 44% |
| 每题停留0.7秒 连续十局 备用题占比 | 0% | 0% |
| 每题停留0.7秒 连续十局 图片唯一率 | 99% | 100% |
| 每题停留0.7秒 连续十局 图片重复率 R_I(50) | 0% | 0% |
| 确定性过期结果复现 是否重复接受芝加哥 | 是 | 否 |

没有证据说明极速冷启动的重复指标已经显著改善。等待上限不增加，而新启动进程也没有已准备图片，因此0.6秒的持续产出赶不上立即切题，仍然需要备用。缓存优先路径在存在未见且可用的已准备图片时才有效，这一条件由自动化测试覆盖。

实施中曾试验只保留20题图片历史并优先使用缓存，备用比例降至20%，但图片唯一率跌至40%。这个方案已被修正。`after-fast`与`after-multigame`目录是中间实验，不是最终结果；最终回放请看 `final-fast` 与 `final-multigame`。

最终版本没有采用以重复缓存图片换取低备用比例的策略。连续十局历史保留和旧标识迁移由测试单独验证。

## 验证和限制

- 全部55项单元与流程测试通过，包括API错误识别、TIFF排除、异常文件隔离、缓存保留、Retry-After、网络失败时缓存复用、预取历史检查和跨局图片历史。
- `git diff --check`通过。
- 缓存仍在进程内，服务器重启后需要重新准备。本次未引入数据库或长期图片存储。
- 固定备用题库仍有20张。断网且没有合格缓存，或冷启动极速切题时，重复依然可能发生。
- 本次未完成全100城浏览器加载测试，也没有真实玩家连续日志，不报告全城实际概率均匀性或声称完全消除图片重复。

涉及核心文件：`app.py`、`city_provider.py`。诊断工具同步适配了错误传播和图片历史长度。

下一阶段宜先收集实际答题节奏下的备用比例、图片唯一率和短期重复率，再决定是否需要增加预备题缓冲或实施城市公平轮换。
