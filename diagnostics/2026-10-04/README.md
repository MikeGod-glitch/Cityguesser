# 图片丰富性与城市分布诊断报告

日期：2026年10月4日。范围：预取回退、城市获取差异及它们对展示结果的影响。

## 结论

1. 预取延迟确实可以把原本丰富的动态题库变成频繁使用固定20张备用图的体验。但没有真实玩家连续日志，不能把受控回放中的回退率当成日常回退率。
2. 城市获取差异不是纯粹的假设。开罗和都柏林已经复现了真实故障：一个TIFF文件的缩略图参数错误导致整个查询失败；程序把API错误当成空图片池，并缓存六小时。
3. 优先修复错误识别和图片准备流程，比立即扩大候选城市数、延长等待时间或重做随机算法更有依据。尚未实施这些修复。

## 一 真实联网证据

### 缩略图错误被当成空题库

原有查询把附近100个文件的资料与1280像素缩略图一起获取。开罗和都柏林均返回 `error.code = urlparamnormal`，错误详情指向一个 CAPELLA TIFF 文件。HTTP请求完成并返回JSON，但没有正常的 `query.pages`。

`_api_get` 没有识别JSON中的API错误；`_fetch_photos` 把缺少 `query.pages` 当成没有文件，保存空数组并设置六小时TTL。真实诊断的再次读取命中了这两个空缓存，没有重新联网。这样一来，原本有图片的城市会被后续抽题流程持续跳过。

只读替代查询实验：先取资料，按现有MIME、尺寸和质量规则筛选，再为一个正常格式文件请求缩略图。

| 城市 | 无缩略图参数时返回文件数 | 其中JPEG / PNG / TIFF | 现有质量规则通过数量 | 抽查正常格式缩略图 |
|---|---:|---|---:|---|
| 开罗 | 100 | 97 / 2 / 1 | 54 | 成功 |
| 都柏林 | 100 | 97 / 2 / 1 | 39 | 成功 |

54和39是图片家族去重之前的候选数，未进行人工画面质量审核，不等于最终可发布题数。缩略图地址获取成功不等于浏览器加载验证成功。替代请求只在独立诊断进程中运行，没有改变游戏查询。

证据：`api-errors/trace.json`、`thumbnail-probe/summary.json`、`survey-slow/trace.json`。

官方接口资料也明确列出了 `urlparamnormal` 错误及JSON错误处理方式：

- [MediaWiki Imageinfo](https://www.mediawiki.org/wiki/API:Imageinfo/en)
- [MediaWiki Errors and warnings](https://www.mediawiki.org/wiki/API:Errors_and_warnings)

### 图片池与限流

两轮扫描共保存了27个城市的286张合格图片，已成功取得的城市图片池大小为3至22张。例如北京3张、阿姆斯特丹4张、芝加哥12张、蒙特利尔22张。

其余城市尚未完整确认，不能填写成0张。开罗和都柏林通过替代查询证实有候选图片，但这些候选尚未按原有路径生成完整题库，因此也没有混入上述286张。

首轮诊断使用两线程、请求间隔0.5秒，遇到HTTP429后未及时停止，累计记录176次429；这些失败不能用于推断城市本身的可用率。降频到单线程、间隔3秒后再次遇到429，此时已立即停止，服务器 `Retry-After` 为28秒。工具现已加入遇到429停止和记录等待提示的保护。

诊断扫描自身的请求量会影响限流，本报告不据此声称普通玩家经常遭遇429。未取得完整100城市快照，因此不报告完整图片分布偏离度或全城市真实可用率。27%只是本次已保存题库的覆盖比例。

原路径的成功署名探测请求耗时约0.44至0.96秒；降频扫描中成功的图片查询本身约1.77至2.37秒。限流等待、失败请求耗时和成功请求耗时分别记录。图片资料缓存命中的读取通常在微秒级，但新的图片仍可能需要署名请求。

## 二 原有游戏路由受控回放

回放通过Flask测试客户端调用原有 `/reset`、`/play`、`/check`、`/next` 路由。答题自动正确，图片库与延迟由诊断进程临时替换，不联网、不修改生产代码。每种场景100题。

“图片就绪”场景设定100城、每城20张虚拟图片，每次准备耗时固定0.6秒。它用于隔离预取时序，不是实际图片库规模，也不是实测完整联网准备耗时。

| 场景 | 每题答题停留时间 | 固定备用题占比 | 因准备未完成回退占比 | 图片唯一率 U_I(100) | 图片短期重复率 R_I(50) |
|---|---:|---:|---:|---:|---:|
| 无尽模式 立即切题 | 0秒 | 50% | 50% | 70% | 42% |
| 无尽模式 留出准备时间 | 0.7秒 | 0% | 0% | 98% | 2% |
| 连续10局十题 留出准备时间 | 0.7秒 | 0% | 0% | 99% | 0% |
| 动态题完全不可获取 | 0.01秒 | 100% | 0% | 20% | 100% |

这些唯一率和重复率是各一次回放的观测值，存在随机与线程调度波动。它们是服务器计划展示的图片指标，未加载真实图片，不代表真实玩家指标。

解释：

- 预取在玩家思考期间运行，因此是否回退取决于准备速度与答题节奏，而不只取决于0.3秒等待预算。
- 即便所有城市都有丰富图片，快速切题也能因为准备未完成而大量退回固定题库。
- 完全不可获取时，100题只有20张不同图片，后50题的每张图在此前50题都出现过。
- 连续开局保留近期图片和城市历史，没有证据表明多局十题本身会无条件清空去重历史。
- 下一题页耗时与首题、重开局耗时应区分；例如多局回放P95包含重新开局时同步准备首题约0.6秒，不能解释成普通下一题预取变慢。

证据：`fixture-fast`、`fixture-paced`、`fixture-multigame`、`fixture-unavailable` 下的 `summary.json` 与 `trace.json`。

### 过期预取结果

另一个确定性实验让预取暂不完成，先展示芝加哥备用题，再完成预取中的芝加哥动态题。原有程序接受该结果并再次展示芝加哥，绕过了最新城市历史。

这确认了消费异步结果时需要重新检查历史。上述100题随机回放没有观测到动态历史冲突，不代表缺陷不存在或已经测出真实发生率。

证据：`offline/summary.json`。

## 三 城市成功率与展示偏差

对原有 `get_random_question` 函数做了两组各30,000次受控抽题。实验只替换图片获取是否成功，不改变候选随机排列和取第一个成功城市的逻辑；没有应用近期城市排除，因此用于识别机制，不代表完整游玩分布。

| 配置 | 四城最终展示份额 |
|---|---|
| 四城成功率均为90% | 25.43%、24.86%、24.65%、25.05% |
| 前两城90%，后两城30% | 40.47%、39.33%、10.16%、10.04% |

获取成功率不同，确实会变成最终展示份额不同。现实中已发现的空缓存误判，会让开罗和都柏林在该进程的动态抽题路径上被跳过；本地20城备用库也不含这两城。

目前没有足够的各城市重复测量及真实展示日志，不能给出100城的真实成功率排名、真实B_C或玩家每天遇到这些问题的比例。

## 四 建议实施顺序

### 第一批 必须先修正的获取问题

1. 显式检查JSON中的API错误。区分错误、暂时失败、真正没有合格图片；错误不得保存成六小时空题库。
2. 将图片资料筛选与缩略图获取分开。先过滤不支持的格式，再为合格文件取缩略图；小批量处理并隔离异常文件。先用开罗和都柏林验证，不一次重写所有逻辑。
3. 保留已取得的有效缓存。刷新失败不替换成空数组；按错误类型设置短暂重试与退避，尊重HTTP429的 `Retry-After`。
4. 尽量把署名资料和缩略图准备放在缓存构建阶段，减少每道新题的额外联网依赖。

### 第二批 修正预取与备用题路径

1. 消费预取结果时检查最新城市和图片历史，冲突结果不得直接展示。
2. 区分准备中与已失败；优先使用已准备的合格图片，固定20图仅作最后兜底。
3. 依据重新测出的任务耗时和真实答题节奏确定等待预算，不简单增加候选尝试次数或把0.3秒改成一个任意值。

### 第三批 再评估城市公平性

修复获取流程后重新构建可复现题库清单，补齐100城测量，再比较各城成功率、图片池大小和展示偏离。若仍明显偏向少数城市，再实施“先公平选择城市、再在该城选图片”的轮换策略。避免用缩小城市范围换取漂亮的均匀性指标。

复现不联网实验：

```powershell
python -B tools/diagnose_randomness.py offline --output diagnostics/reproduce-offline
python -B tools/diagnose_randomness.py live --fixture ready --fixture-delay 0.6 --questions 100 --think-seconds 0 --output diagnostics/reproduce-fast
python -B tools/diagnose_randomness.py live --fixture unavailable --questions 100 --think-seconds 0.01 --output diagnostics/reproduce-unavailable
python -B -m unittest discover -s tests -q
```

联网扫描应单独运行，维持低并发与退避，不把本次限流后的未知城市当作无图片城市。游戏修改需另行确认。
