# 库存优化量化验证

日期：2026-10-06，时间均为北京时间。范围：最近一次持续补库、共享请求节奏、库存优先预取及候选持久化改动；不把此前放宽筛选或提高库存目标的效果混入对照。

## 结论

真实运行文件显示库存仅小幅增加，尚不能证明线上玩家的图片重复率显著改善。受控回放验证了持续补库的机制收益，但其无网络失败条件不能代表当前外部 API 的实际成功率。

## 一、真实库存观察

改动前数值来自本聊天 16:39:12 的只读统计记录。改动后数值来自 17:08:29 读取的库存文件，按未过期照片统计。不同时间的观察不是严格同时进行的线上 A/B 实验。

| 指标 | 改动前 16:39 | 改动后 17:08 | 变化 |
|---|---:|---:|---:|
| 可用库存照片 | 205 | 219 | +14，+6.83% |
| 城市覆盖 | 100 | 100 | 无变化 |
| 每城照片中位数 | 2 | 2 | 无变化 |
| 库存不超过 2 张的城市 | 77 | 79 | 未改善 |
| 库存至少 12 张的城市 | 0 | 0 | 无变化 |
| 达到 24 张目标的城市 | 0 | 0 | 无变化 |

17:06:23–17:08:29 的额外观察中，库存持续为 219 张，净增 0。统计文件的更新时间停留在 17:03:59，记录含 API 退避错误。这个观察只能确认文件没有新增，无法区分进程停止、退避或休眠等原因；也不能把不同时长、可能跨进程重载的错误计数比较成失败率。

输入候选缓存包含 20 个城市、1,026 张候选。候选丰富不等于准备完成的库存丰富。

## 二、同一输入下的补库对照

两组从同一份真实 219 张库存和相同候选快照开始，筛选规则、目标 24 张及城市优先级保持一致。只为候选快照已确认的 20 个城市补库，不把其他城市未知的候选数当成零。

受控条件：10 分钟虚拟时间、没有后续页面请求、缩略图元数据准备每次耗时 0.5 秒且全部成功。API 响应被隔离进程替换，未发送真实联网请求、未加载真实图片。

旧策略执行一批最多 24 次准备，之后等待下一次页面请求；新策略执行实际生产的持续补库循环。每组使用 5 个随机种子，结果一致：

| 指标 | 旧策略 | 新策略 | 变化 |
|---|---:|---:|---:|
| 成功新增照片 | 24 | 132 | 5.5 倍 |
| 最终库存 | 243 | 351 | +108，+44.44% |
| 库存不超过 2 张的城市 | 59 | 59 | 无变化 |
| 库存至少 12 张的城市 | 0 | 0 | 无变化 |

这主要验证了“无需后续页面请求即可继续补库”。不证明真实联网环境一定每 10 分钟新增 132 张，也没有量化共享限速减少 HTTP 429 的幅度。没有成功的外部请求，调度优化仍不能兑现这份潜在收益。

## 三、重复率对照

对上述旧、新库存分别执行 30 轮抽题，每轮 1,000 题，使用实际 `get_cached_question` 和 `PhotoRotation`，保留最近 100 张图片及最近 20 个城市的历史。库存为固定快照，游玩期间不继续补库。先随机选符合条件的城市，再随机选该城市的未看过图片。

重复按相同图片 ID 统计，不检测不同文件的相似画面或同一地标。

| 指标，30 轮均值 | 旧策略补库后 | 新策略补库后 | 变化 |
|---|---:|---:|---:|
| 最近 100 题内同图重复率 | 0% | 0% | 无变化，原有去重有效 |
| 最近 200 题内同图重复率 | 48.90% | 41.53% | −7.37 个百分点 |
| 1,000 题累计重复比例 | 75.70% | 65.43% | −10.27 个百分点 |
| 1,000 题不同照片数 | 243 | 345.73 | +102.73，+42.28% |
| 无库存可抽的请求比例 | 0% | 0% | 无变化 |

“累计重复比例”定义为 `(展示总数 − 不同图片数) / 展示总数`；不是“紧接着重复”的比例。200 题窗口重复率只统计从第 201 题开始、图片在此前 200 题出现过的情况。

另外，对真实 219 张库存快照单独做同样回放：最近 100 题内重复率为 0%，1,000 题累计重复比例为 78.10%，200 题窗口重复率均值为 56.25%。这表示固定 219 张库存最终会反复轮换，不代表实时游玩过程（其中可能继续补库）的实际重复率。

缺少精确的旧库存图片 ID 和改动前后玩家序列，因此不能提供真实线上重复率的因果改善数字。

## 四、重启候选复用

隔离进程清空内存候选后，按当前版本校验从真实候选文件恢复：20/20 个城市、1,026/1,026 张候选。逐城调用实际 `_fetch_photos`，API 请求次数为 0。旧机制没有候选持久化，重启后的这些城市需重新发现候选。

这验证了候选复用，不代表 1,026 张候选已经全部变为可展示库存；署名和缩略图准备仍需要完成。

